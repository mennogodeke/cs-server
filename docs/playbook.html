cs‑server / playbook.md

Infra plan · Counter-Strike 2 · Sept 2026

A private CS2 server that only exists while you play

One instance, spun up with a single command before a session and destroyed after — configurable from 3v3 to 8v8. The game files wait in a cheap snapshot; a reserved IP keeps the connect string constant. Around €5 a month for typical use.

players: NL / DE border format: 3v3 → 8v8 + practice lifecycle: on-demand (create/destroy) mgmt: Terraform + Compose host: Hetzner

01 · The short version

Rent it by the hour, delete it after

Run one CS2 instance on a small Hetzner box that you create before a session and destroy after. Hetzner bills cloud servers hourly and keeps charging for a stopped server until the server object is deleted — so "off" has to mean gone, not powered down. Between sessions almost nothing is running: a ~€0.75/mo snapshot holds the installed game, mods and configs, and a ~€0.50/mo reserved IP keeps your friends' connect string stable. A one-command gameday up / gameday down wrapper around Terraform drives the lifecycle.

One box, hourly, dedicated cores

Hetzner CCX13, created on demand

  • CCX13 — 2 dedicated vCPU, 8 GB, Falkenstein or Nuremberg (~15–25 ms from the NL/DE border). ~€0.066/hr, so a 4-hour game night costs about €0.26. Dedicated cores keep CS2's sub-tick simulation smooth — no noisy-neighbour stutter mid-clutch.
  • Base image: a golden snapshot with the game + pinned mod stack baked in. Boots to playable in 3–4 minutes.
  • Stable address: a reserved Primary IP (auto_delete = false) or a Floating IP, ~€0.50/mo, reassigned to each new server.
  • Format per session: gameday up --format 6v6 --map de_nuke — a Terraform variable flows through cloud-init into the server config and MatchZy's players_per_team.
stop ≠ free

A powered-off Hetzner cloud server bills at the full hourly rate until you delete it — the CPU/RAM/NVMe stay reserved for you. The on-demand pattern is create/destroy, not start/stop. Pair it with a nightly "reaper" that destroys any server left running (§09).

the lazy alternative

If the orchestration isn't worth it to you, an always-on CX32 (~€6.80/mo, 4 shared vCPU, EU-only) is the zero-effort option — always ready, fine for casual 3v3–8v8, a little risky for tight competitive rounds because the vCPU is shared.

02 · What "private" requires

Still a public, token-authenticated server

"Private" means password-gated, not network-isolated. Unless everyone is on your LAN, the server runs in internet mode:

  • One GSLT. A Game Server Login Token (Steam → manage game servers, App ID 730) is required for sv_lan 0 even on a passworded server. With a single instance you need exactly one token — bake it into the snapshot or inject it from secrets at boot.
  • sv_password gates entry: connect <ip>:27015; password <pw>.
  • There is no 128-tick. CS2 uses a sub-tick model. Don't pay a premium for "128-tick" hosting — what matters is uninterrupted single-core CPU time.

03 · Where to host

Hourly billing changes the answer

Because you pay by the hour, the monthly sticker price stops mattering and you can rent a dedicated-vCPU plan you'd never keep full-time. CS2's simulation is effectively single-threaded and the sub-tick system needs every inbound packet handled immediately — per-core clock and uninterrupted core time win, and shared vCPU risks steal-induced "var" spikes mid-round. A CCX13's two dedicated vCPU cost about €0.066/hr — pennies per session — and take that risk off the table.

Round-trip from the NL/DE border: Hetzner Falkenstein / Nuremberg ~15–25 ms (no NL region); Netcup / OVH / Vultr Amsterdam ~5–15 ms. The gap isn't decisive for a friends' server, and Hetzner earns its place on tooling: a first-class Terraform provider, free automatic DDoS mitigation, an edge firewall, and true hourly billing with a monthly cap.

04 · The on-demand lifecycle

Create, play, destroy

The server exists only while you're playing. Everything that must outlive it lives in one of three places: your Git repo (configs, Compose file, pinned mods), a snapshot or volume (the installed 60 GB game), and a couple of always-allocated cheap resources (the reserved IP, the firewall, an optional demo store).

Keeping the game between sessions

A session, end to end

  1. gameday up --format 6v6 --map de_nuke — Terraform creates a CCX13 from the snapshot, reassigns the reserved IP, applies the firewall.
  2. cloud-init pulls the repo, decrypts secrets (SOPS), writes the session env, runs docker compose up -d. CS2 self-updates; a health check confirms Metamod + CounterStrikeSharp loaded (else it starts the vanilla profile so the night isn't lost).
  3. The script prints — or posts to Discord — connect cs.example.net; password …
  4. Play. sv_hibernate_when_empty keeps the core idle until people join.
  5. gameday down — rsyncs demos to the Storage Box, then terraform destroy removes the server (and volume, if used). IP, snapshot and firewall stay.
run it from your phone

Wrap gameday up/down in a GitHub Actions workflow_dispatch with format and map inputs. Trigger the game night from the Actions tab or a phone; the workflow posts the connect string to Discord.

The joedwards32/cs2 image runs as a non-root steam user, updates the game on container start, and exposes everything through environment variables (SRCDS_TOKEN, CS2_RCONPW, CS2_PW, CS2_MAXPLAYERS, CS2_STARTMAP, GOTV settings…). One service, two profiles: full (with mods) and vanilla (fallback for the days a CS2 patch breaks Metamod). Bake the pinned addons/ tree into the golden snapshot so no mod install happens at boot.

06 · The mod stack

Metamod → CounterStrikeSharp → MatchZy

  1. Metamod:Source (dev branch) — the loader, registered in gameinfo.gi.
  2. CounterStrikeSharp — the C# plugin runtime nearly every current plugin targets.
  3. MatchZy — the de-facto get5 successor: knife round, side pick, pause / tech-pause, per-match configs, demo recording. Practice mode is built in (.prac / .exitprac: nade spawns, bot placement, trajectories). It supports 1v1 through 5v5 natively (auto-pause is 5v5-only); players_per_team is configurable.
  4. Optional: cs2-retakes, a deathmatch plugin for warmup, CS2-SimpleAdmin for bans / kicks / map changes.

With a single instance you run one mode at a time — switch between practice, retake and match with exec configs, driven by gameday up --mode.

the recurring gotcha

Most large CS2 patches break Metamod and CounterStrikeSharp until both rebuild (symptom: an undefined symbol load error, seen repeatedly through 2026). You can't pin the game — the server must match the client build. On-demand actually helps: you find out at gameday up time, and the health check drops you to the vanilla profile so casual play still works. Rebuild the golden snapshot once the mods catch up.

07 · Repo & provisioning

Bootstrap once, session on demand

cs-server/
  terraform/
    bootstrap/          # applied once: reserved IP, firewall, SSH key, Storage Box
    session/            # ephemeral: the server (+ volume attach); apply / destroy per game night
  packer/               # golden-image build: base OS + CS2 + pinned addons -> snapshot
  cloud-init/           # runs on boot: compose up, session env, mod health-check
  compose/
    docker-compose.yml  # one service: cs2 (+ gotv)   profiles: [full, vanilla]
  cfg/                  # server.cfg, prac.cfg, retake.cfg, match_*.cfg, gamemodes_server.txt
  addons/               # PINNED: metamod/ counterstrikesharp/ MatchZy/ ...
  secrets.enc.env       # SOPS + age: GSLT, rcon_password, sv_password
  bin/gameday          # up | down | build | status  -> wraps terraform -chdir=terraform/session
  .github/workflows/    # lint on PR; workflow_dispatch: gameday up/down with inputs; nightly reaper
  • Split state. gameday down runs terraform -chdir=terraform/session destroy and never touches the IP or firewall in bootstrap/.
  • Reserved IP: hcloud_primary_ip with auto_delete = false (or hcloud_floating_ip), read by the session config through a data source and reassigned on each create.
  • Golden image: Packer's Hetzner builder boots a temp server, installs the game + pinned mods, snapshots, destroys. Re-run when you bump mod versions — gameday build is a thin wrapper.
  • Secrets: SOPS + age; decrypted on the server at boot, never plaintext in Git.
  • State backend: Terraform Cloud free tier, or Cloudflare R2 / Backblaze B2 (Hetzner has no S3).

09 · Operations

The safety nets that make on-demand safe

The reaper

  • A scheduled GitHub Actions job (hourly) runs hcloud server list and destroys any cs2-session server older than N hours, or empty (RCON player count 0) for 30 minutes. This is the single most important piece of the on-demand model.
  • Worst case without it: a CCX13 left running a whole month ≈ €15 (Hetzner caps hourly at the monthly rate) — annoying, not ruinous. The reaper makes it a non-issue.

Game & mod updates

  • CS2 self-updates when the container starts — every gameday up is on the current build.
  • The boot health check verifies Metamod / CSSharp; on failure it starts the vanilla profile.
  • Rebuild the golden snapshot (gameday build) whenever you bump pinned mod versions — every few weeks.

Demos & backups

  • gameday down rsyncs demos/ to a Storage Box (BX11, 1 TB, ~€3.80/mo) before destroying — or, with the Volume approach, they persist there automatically.
  • Configs + addons are in Git; the snapshot is reproducible from Packer.

Monitoring

  • Short sessions make heavy monitoring pointless. Pull stats over RCON during a match; if sv variance climbs on a shared-vCPU plan, move up to CCX13 / CCX23.

10 · Security checklist

Before you hand out the IP

  • Firewall lives in bootstrap/ (long-lived): game + GOTV UDP to the world, SSH to your IP / WireGuard only.
  • SSH: key-only, PermitRootLogin no, PasswordAuthentication no, fail2ban.
  • Containers run as non-root (image default steam, uid 1000); never mount docker.sock.
  • Unique 24+ char rcon_password and sv_password, generated, stored in SOPS.
  • RCON reachable only via WireGuard / a single admin IP — never public.
  • Treat CounterStrikeSharp plugins as arbitrary code in your server process — install only from reputable repos, pin to a release tag or commit hash.
  • The reaper doubles as a security control: the box simply doesn't exist most of the time.

13 · Next steps · once the server works

Player tracking via GSI

A separate side project already exists: a Swift CLI running a small webserver that implements Valve's Game State Integration (GSI) — it receives JSON POSTs and tracks either personal in-match stats or full server/team stats while spectating. The idea is to point it at this server once game nights are actually happening.

sync first

Nothing below is committed to. This section exists so the idea isn't lost, not as a queued task — sync up before building any of it, once the base server (§12) is actually working.

The one thing worth internalising now, since it shapes every option below: GSI is a client-side feature. The JSON POSTs come from each person's local CS2 client, via a gamestate_integration_*.cfg dropped into their own csgo/cfg/ — not from the dedicated server. The receiver's address has nothing to do with the game's connect string; it's just an HTTP endpoint the client is told to talk to.

If the client-config route is picked, the receiver most likely lives on the ephemeral session box itself: bind it to the existing reserved Primary IP on a second port, add one firewall rule alongside 27015/27020, and it inherits the same create-with-the-session, gone-when-you're-done lifecycle as the game itself — no separate always-on box or home-network port-forwarding.

  • A gameday gsi-config [--name friend] command that prints a ready-to-paste gamestate_integration_*.cfg, with the reserved IP baked in and a token per friend (so access can be revoked per-person without touching everyone else's file).
  • The receiver as one more service in compose/docker-compose.yml, started by the same cloud-init as the game container.
  • Decide later whether the CounterStrikeSharp-plugin path (richer, no client install) should replace the per-client GSI files once phase 7 lands, or the two coexist — GSI for personal perspective, the plugin for full-server spectating stats.
